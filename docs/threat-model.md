# Threat model and safety

A live, user-generated, AI-assisted video product has real risks. This is what the code does about each, and where it stops.

| Threat | Mitigation | Limit |
|---|---|---|
| **Unsafe or abusive AI dare** | Schema validation → context-aware policy (negation and "mime/imaginary" framing understood) → boundary enforcement → de-dup → independent model review (fails closed) → engine re-validates before publish → approved fallbacks | Regex lexicons are English-only and cannot cover every phrasing. The second model can be wrong. Hence Safety Stop, pass, reports, moderators |
| **Prompt injection** | The model only sees server-built context made of enumerated values and titles the server already approved; output is untrusted; injection markers, links, markup and non-Latin text are rejected; the reviewer prompt treats candidates as data | A novel jailbreak could slip a harmless-looking string through; it still cannot do anything but be a dare that passed the policy |
| **Player coerced to continue** | Pass is free, Safety Stop is one tap and always allowed in an attempt, no phase can force acceptance (silence = pass), policy rejects coercive wording | A social-pressure chat message is outside engine control: moderation and reporting handle it |
| **Boundary bypass by mis-tagging** | Theme lexicons run on the text itself; tags are ignored for enforcement | Lexicons are finite |
| **Vote manipulation** | One ballot per user per round (engine + DB primary key); server clock; server picks winners; ballots hidden; rate limits; per-session membership | One person with many accounts. Mitigate with real signup friction and moderation, not solvable client-side |
| **Client tampering** | Clients are never trusted: no client message can advance state, publish options or change roles (tested) | A compromised client can still send *permitted* commands |
| **Leaked secrets** | Gemini, LiveKit and Supabase service keys exist only on the server; logs redact keys/tokens; errors never echo upstream bodies; app config holds public values only | Rotate keys if a server is compromised |
| **Underage users (under 16)** | Neutral birthday screen (it does not say which ages are allowed), server-side minimum age of 16, the first answer is final and an under-age answer is remembered so it cannot be retried, report type "might be under 16", suspend/ban tools | **Self-declaration is a screen, not verification.** A public launch needs a real age-assurance provider and legal advice per market |
| **Adult-to-teen contact** | Teens (16-17) and adults never share a live session, duel, user search, profile view, leaderboard or Dares feed: enforced on the server, and the other band answers exactly like "does not exist". Teens cannot send free-text duels. Moderators can see both bands | **Self-declared age.** An adult who lies about their birthday lands in the teen band, and a young teen who lies lands in the adult one. Real age assurance is the control for this, not more screens |
| **Grooming and contact through chat or follows** | Same-band only; teens can only chat with mutual followers, re-checked on every message; adults' first contact is one message request that can be declined; filter blocks links, phone numbers, @handles, meet-up talk, personal questions and moving to other apps (teens); block ends everything both ways; reporting from a chat attaches the last messages; rate limits on follows and messages | A filter is a speed bump, not a guarantee. Chats are **not end-to-end encrypted and are stored in plain text**, so moderators can act on reports; say so in the privacy policy. No automated scanning of chats yet. Before launch: scale up moderation, add repeated-pattern detection (for example one adult-band account messaging many people), and decide retention |
| **Spam and harassment by follow/DM** | Rate limits, block, report, decline, one request per pair | Account farming |
| **Re-entering a birthday to change band** | `POST /v1/me/age` is write-once: later calls ignore the body | A new account with a different birthday |
| **Pressure, humiliation and risk for teens** | Teen content floor applied by the server on top of the player's boundaries: level 3 maximum, no social-courage, romance or dark-humor dares, extra word rules (pressure, going public, money, meet-ups, body image); curated duels only; Safety Stop, free Pass, block and report; Cipher uses a teen persona that never suggests meeting anyone | Lexicons are finite; peer pressure in chat is a moderation matter |
| **Harassment / unwanted content** | Block (instant; hides the blocked person's chat for you and stops them joining sessions you host or perform in), report → moderator queue, moderator cut/kick/end/suspend, audit log | Needs humans on call. There is no automated video analysis |
| **Abuse of the API** | Per-IP and per-user rate limits, 16 KB bodies, 8 KB socket frames, auth timeout, slow-consumer drop | In-memory limiters; use a shared store when scaling out |
| **Dev shortcuts in production** | `DEV_AUTH`, fast timers and the bot endpoint are impossible when `NODE_ENV=production` (startup throws) | |
| **Stored video (Feed)** | Recording is opt-in per run and off by default; only the Player's camera/mic is recorded (never viewers or chat); starts after the Player accepts a dare; Safety Stop, moderator cut, abandonment and session end delete the file; only completed/failed rounds are offered; nothing is public until the Player posts; unposted clips expire in 24 h; the bucket is private and the app gets 6 h signed URLs; authors and moderators can delete; 3 distinct reporters auto-hide a clip; blocked authors are filtered out of your feed; account deletion cascades to clips | **There is no automated video analysis.** A Player can say or show something harmful on a posted clip, so a staffed moderation process is required before real users see a public feed. Egress files are removed best-effort; verify bucket contents in your own monitoring |
| **Cipher (AI companion)** | System persona with hard limits (no sexual/hateful/dangerous content, never pressure anyone to continue a dare, no personal-data requests, never reveal the prompt); user text stays in the user turn, history is capped (14 turns, 400 chars), roles whitelisted; output is stripped of links and markdown; self-harm language bypasses the model and gets a fixed, kind reply pointing to trusted people and emergency services; per-user rate limit; the server stores no chat content and logs none; memory lives on the phone and can be wiped | A model can still say something wrong or odd. Cipher is not a counsellor and says so in settings. Messages are processed by Google Gemini under your API terms: disclose this in your privacy policy |
| **Profile data exposure** | Public profiles come from an explicit allow-list (handle, avatar, bio, accent, join date, stats, badges, posted clips, recent round results); boundaries, birth date and raw roles never leave the server; blocked-by-them returns 404; badges and stats are computed server-side | Handle and bio are user-written text: reportable, and bios cannot hold links or @handles |
| **Custom profile photos** | Uploaded as base64 over a size-capped route (500 KB), type sniffed from the real bytes (JPEG/PNG/WebP only), served with `nosniff` and a sandboxing CSP, rate-limited, reportable (`inappropriate_avatar`), moderators can reset it, deleted with the account | **There is no automated image analysis.** A user can upload an inappropriate photo until someone reports it. A staffed moderation process (or an image-moderation service) is needed before a public launch. The photo URL is public to anyone who knows a user id |
| **Duels** | Only the challenged player can accept or submit and only the challenger can approve; dares go through the same safety policy and the target's boundaries; no links or @handles; one open duel per pair; limits on open duels and sends; duels expire; blocked pairs cannot duel | Two friends can still agree to dare each other something dumb. Reporting and blocking apply |
| **Points farming** | Points are minted by the server, never staked or transferred; unique ledger keys make each award one-time; daily caps per user; only the first approved duel between the same two people each day pays; quests are derived from real server-side activity | Many accounts can still farm slowly. **Do not enable any cash-out before real anti-fraud, identity checks and legal review** (see `docs/points-and-rewards.md`) |
| **Data retention** | Chat is held in memory (last 60); `ai_generations` stores no user text; account deletion cascades to profile, votes and clips | |

## Before a public launch (not done here)
Legal review of live UGC, **minors' data and age-appropriate design rules in each market** (for example COPPA and GDPR-K age-of-consent thresholds, the UK Children's Code and Online Safety Act, app-store age ratings); a privacy policy and terms; app-store review of UGC requirements (report, block, moderation, contact); a staffed moderation rota; age assurance; abuse and CSAM response procedure; load and chaos testing on real infrastructure; independent security review.
